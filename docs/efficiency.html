Method

  1. Fixed, read-only, repo-local task set in three difficulty tiers (trivial / aggregate / reason); identical prompts run through both configs, so any delta comes from the harness layer.
  2. Two configs: stock (bare engine, JSON mode) vs torus (same argv plus the canonical child extension set — byte-for-byte the spawn a delegation receives).
  3. Warmup discarded: one warmup run per task × config runs first and is excluded from statistics (steady-state prompt cache, warm extension load path).
  4. Interleaved rotation: measured passes alternate config order (stock, torus / torus, stock / …) so provider-side prompt-cache drift cancels across configs.
  5. Medians with spread: cells are medians ± half the interquartile range over measured runs; a delta is labeled signal only when it exceeds the larger config's IQR.
  6. Shared reducer: usage and cost fold out of the JSON event stream via the production reduceEngineEvent pipeline.

Caveats. Cache read/write deltas remain indicative: provider prompt caches can survive between runs, and torus's larger declaration surface inflates fresh-cache writes by construction. Tokens-in and cost deltas are the stable signals. Wall-clock includes extension loading at spawn. Numbers are self-reported by the engine per run.

Self-contained report — no external assets. Raw per-run records ship in the JSON sidecar.
